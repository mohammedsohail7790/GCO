**1 Nov 2026: #6 CSV export service: built and tested (not yet committed).**
- **What it does.** On the billing screen a CEO_ADMIN can download four CSV files for one client and period (up to 3 months): usage, invoices, reconciliation and operator earnings. Step 1 (`POST /api/v1/admin/exports`) checks permission (BILLING_MANAGE), client and period, writes an audit entry (`export.requested`) and returns a link. Step 2 (`GET .../download`) honours the link only for the same signed-in user, within 10 minutes and for the exact filter authorised, checks the permission again, writes `export.downloaded` with the row count, and returns the file with `no-store`.
- **Retention.** Nothing is stored: the file is produced again at download, so there is nothing to purge and no file that can leak later. Limit: 50,000 rows per file (else "choose a shorter period").
- **Safety.** Text cells that start with = + - @ are neutralised so a spreadsheet cannot run them as formulas; the link key is separate from the session key; no migration.
- **Evidence.** Unit `exportCsv` (7: quoting, formula guard, link valid/other user/expired/tampered); E2E `57-csv-exports` (4 passed): usage total (45 cents for 3 messages at 15) equals the reconciliation screen, audit entries exist, other roles refused and a link is useless to them, tampered/garbage link and bad periods refused. Checked by hand on the demo stack: admin gets the file, a manager holding the link gets 403. Typecheck and lint clean.

**1 Nov 2026: flaky `earningsLedger` concurrent-payout test: cause found and fixed (test only; no product change).**
- **Reproduced** by running the test repeatedly with the worker stack running (failed on run 5 of 12; it never failed in 8 clean full integration runs without the stack, so load timing matters).
- **Cause:** the payout was closed "up to now" using Node's clock (milliseconds, truncated) while the database stamps new rows with `CURRENT_TIMESTAMP` at millisecond precision, rounded. A row created a fraction of a millisecond earlier can therefore carry a time just after "now" and be left out: the failing run showed only the last adjustment (+100) missing (payout 25 instead of 125). **In production this is harmless** (that adjustment is settled in the next payout; nothing is lost or paid twice, and the claim step stays race-safe), so no change to the ledger.
- **Fix:** the test closes the period 5 seconds ahead. **Evidence:** 25 of 25 passes with the worker running, where it previously failed about 1 in 5 to 12.
- **Harness note:** integration tests must be run without the stack's AI/dev-adapter settings in the environment (a run with them set made `aiDisabled` and `integrationEnvironment` fail for that reason, not because of the code). The E2E `46-executive` set-up failure is still not investigated.
