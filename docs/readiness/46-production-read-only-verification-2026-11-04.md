# 46 — Production read-only verification of what is deployed (4 Nov 2026)

**Authority:** CEO, 4 Nov: strictly read-only; no installation, deployment, configuration change, database change, export of sensitive information or access to credentials.
**Method (what I did):** 165 API routes taken from the repository were requested with a plain **unauthenticated GET** against the public production site and against the local release-candidate copy, and the answers compared. `404` on production where the local copy answers `401/405` means **the route does not exist in production**. `401` or `405` on both means it does. No login, no data read, no write; the only response bodies read were the public health page. Roughly 330 requests in total.
**What this cannot show:** which commit is deployed (needs the server), which database migrations are applied, whether a route's behaviour matches the release candidate, or page-level (screen) differences (pages redirect to the login page whatever they are, so they cannot be told apart). The public health page on production has **no** `environment` or `ai` fields, unlike the release candidate, which agrees with production running the older version (`d9af8dc`, 12 Oct). A server-level check (deployed commit, container image tags, migration list, backup timer state) would need SSH from the CTO's machine using the read-only assessment script `scripts/server-readonly-assessment.sh`, which prints no secrets; it was **not** run: no server login was authorised in this session beyond the public site.

## Findings
**Present in production (LIVE)** (route exists): sign-in and two-step sign-in (`auth/2fa/*`), invitations, staff accounts; tenants and tenant settings; webhook integrations (list, adapters, verify, secret, onboarding/go-live); conversations (list, search, resolve, reopen, resume, notes, transcript, "needs attention"); sending messages; assignments (reassign); operators, **language coverage**, operator status and workspace; **escalations**; **QA** (queue, reviews, summary); **tickets**; **client reporting** (`reports/client`, `usage/summary`); analytics overview; audit logs; system health and dead-letter recovery; the sales/CRM pipeline (leads, approvals, commissions, dashboards); public contact and careers forms.
**Not in production (BUILT, release-ready)** (route absent): shifts and absences (plans, coverage); assignment transfer; operator team and colleagues; knowledge base; training modules, qualifications and operator training; moderation (queue, appeals, client summary); shift handovers; client requests; client invoices, live view, data requests, moderation summary; weekly reports; billing back office (invoices, issue, pay, void, settings, reconciliation); operator earnings, rate cards, payouts; executive overview and search; privacy requests, retention and anonymisation; notifications; alert routes; client setup wizard; **CSV exports; integration sandbox/production environment (and stored check history)**; staging simulator. 75 routes in total.
**Planned (not built anywhere):** configurable QA scorecards and appeals, client-specific SLA reports, downloadable client reports, native channel connectors (WhatsApp, Meta, Shopify, Zendesk, Gorgias, Intercom), a general public API beyond the webhook and callback.
