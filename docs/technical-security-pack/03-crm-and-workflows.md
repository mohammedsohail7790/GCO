# 03 — CRM and business workflow architecture

All rows are **Verified** by automated tests in a local environment unless marked. "Dev-mock" means the simulated client platform; **no real client has been connected.**

| Workflow | Actors / permissions | States and transitions | APIs and persistence | Audit | Failure behaviour | Limits |
|---|---|---|---|---|---|---|
| **Hunter lead ownership** | Hunter (own leads), manager/CEO (all) | NEW → CONTACTED → … ; owner set server-side, 30-day lock | `/crm/leads*`; `Lead`, `LeadHistoryEntry` | stage and owner changes | duplicate lead detection; a worker sweep releases expired locks | lock timing proven with a test clock |
| **Pipeline and Closed Won** | owner moves stages; sensitive stages need manager approval | … → CLOSED_WON (approval) | `/crm/leads/[id]/stage`, `/crm/approvals`; `Approval` | approval decisions | transitions validated; cannot skip approval | — |
| **Payment → commission → payout approval** | manager/CEO confirm payment; CEO approves payouts | PENDING → APPROVED/PAID | `/crm/leads/[id]/confirm-payment`; `Commission` (rate snapshotted, amount server-calculated) | yes | retry and concurrent confirmation create exactly one commission | manual approval by design |
| **Client onboarding** | CEO/assistant; client contact invited; **go-live CEO only** | closed-won → handoff job → provisioning → checklist → LIVE | worker `bpoHandoff`; `ClientOnboarding`, `Tenant`, invitation (hash only) | each step | idempotent; nothing active until explicit go-live; integrations never auto-created | go-live checklist includes a verified integration — dev-mock only today |
| **Client setup wizard** | CEO | one validated request creates tenant, services, rates, invitations | `/admin/clients/setup` | yes | validates everything first; partial invitation failures reported | — |
| **Operator onboarding** | public application (rate limited) → CEO review → staff invitation → training gate | NEW → REVIEWING → decision; operator cannot go available until required training/approval done | `CareerApplication`, `StaffInvitation`, `TrainingAssignment` | yes (ids only) | spam/duplicate handling; one-time invitation links | no email is sent by the platform unless SMTP is configured |
| **Operator queue assignment** | system; operator capacity default 2 (configurable) | QUEUED → ACTIVE (assigned) → WAITING_FOR_CLIENT; language routing; on-shift preference | `Assignment`; per-operator locked capacity check | history entries | race-safe; no operator → stays queued, retried every 15 s | assignment policy intentionally simple (load balancing) |
| **SLA expiry and escalation** | system; manager resumes | ACTIVE → EXPIRED → reassign; after **5** consecutive expiries → SLA-capped (needs manager) | timeout job, `needs-attention` list | `assignment.expired`, one `conversation.sla_escalated` | idempotent; bounded; survives restarts | cap configurable 1–50 |
| **Supervisor review, escalation, client handoff** | operator → supervisor/manager → CEO/assistant → client decision | OPEN → CLAIMED → RESOLVED, level raised | `/escalations*`; `Escalation`, events | yes | role-shaped views (client sees client-safe text only) | — |
| **Conversation lifecycle** | operator, manager | QUEUED/ACTIVE/WAITING/CLOSED; reopen by manager | `/conversations*`, `Message`, `MessageEvent` | yes | tenant-scoped 404 | — |
| **Webhook intake and delivery** | client platform → GCO; GCO → client callback | RECEIVED → … DELIVERED / FAILED | `POST /webhooks/[integrationId]`, outbound worker; `WebhookEvent` | yes | invalid signature rejected before persistence; duplicates ignored; bounded retries → dead letter | real client behaviour unknown |
| **Moderation** | operators claim batches; supervisors resolve | PENDING → IN_REVIEW → DECIDED/ESCALATED; appeals reviewed by a different person | `/moderation/*`; `ModerationItem`, decisions append-only | yes | idempotent ingest; stale claims return after 15 min | **verdicts are not sent back to a client platform** |
| **Operator pay and client billing** | CEO | effective-dated rate cards; payable states; adjustments; payouts; invoices with gap-free numbers | `/admin/earnings*`, `/admin/billing*` | yes | immutable snapshots; concurrent payouts claim rows once | **commercial invoices only — fiscal e-invoicing not implemented** |
| **Retention and erasure** | CEO; clients raise requests | policy per client; request → execute | `/admin/privacy*` | counts only | idempotent; billing/earnings kept | **not activated; policy pending legal review** |

Permissions summary (who can do what) is the matrix in `lib/auth/rbac.ts`; CEO-only: rates, payouts, invoices, privacy, client creation, go-live, AI settings (none: AI is off).
