# 04 — API integration process (connecting a client or provider)

## The standard process
1. **Requirements discovery** — which channel/product, volumes, languages, hours, what operators may see/do, retention and privacy needs (`../GCO_CLIENT_DISCOVERY_PACKAGE.md`).
2. **Provider API and webhook documentation review** — obtain the real specification; GCO does not guess authentication, payloads, ids or signatures.
3. **Authentication and permissions assessment** — which credentials, scopes, expiry, rotation.
4. **Data mapping and tenant boundaries** — external user/message ids → GCO conversation/message; one integration = one tenant.
5. **Sandbox credentials and test environment** — a client-provided sandbox, never production data.
6. **Inbound event verification** — signature (and timestamp where the provider supports it), size limit, schema validation, duplicate handling.
7. **Outbound delivery and response handling** — HTTPS only, SSRF-safe destination checks, timeouts, mapping the provider's success/failure semantics to GCO delivery status.
8. **Idempotency, retries and failure recovery** — external ids, bounded retries with backoff, dead-letter and manual recovery.
9. **Security and privacy testing** — tenant isolation, secret handling, logging review, retention agreement.
10. **End-to-end acceptance testing** — scripted scenarios with the client: inbound → operator → reply → delivery → billing record; failure and retry cases.
11. **Monitoring and operational handover** — alert routing, who is notified, incident contacts.
12. **Production approval and rollback planning** — explicit CEO go-live; the integration stays inactive until verified (`Integration.status`).

## What exists today (verified against tests, not against a real client)
| Piece | Description | Status |
|---|---|---|
| `IntegrationAdapter` boundary | one interface for verify/normalise inbound and send outbound; adding a client = a new adapter, no core change | Verified |
| `dev-mock` adapter | development/test simulator; **refused in production** | Verified (test double) |
| **`gco-webhook` (generic)** | a documented, signed HTTP contract: `X-GCO-Timestamp` + `X-GCO-Signature: v1=HMAC-SHA256(secret, "<timestamp>.<body>")`, ±5-minute replay window, ≤100 events per request (1 MB), events `{event_id, message_id, user_id, text, lang?, sent_at?}`, signed outbound callback to an HTTPS URL the client registers; connectivity pings; staged integrations accept only a signed ping until go-live | Implemented; **tested with local test servers only** |
| Moderation feed | signed `POST /moderation/ingest/{id}` using the same adapter verification; payload is a **GCO proposal** to be confirmed per client | Implemented; proposal unvalidated |

**A generic adapter does not prove that a named provider integration exists.** GCO has not integrated WhatsApp, Instagram, SMS, email or any specific chat/CRM product.

## Still required for the first real client (all **Blocked** on the client)
- The client's API/webhook documentation and a sandbox; how they authenticate; their event and error formats; rate limits.
- A decision whether the client implements the `gco-webhook` contract or GCO writes an adapter to their API.
- Credentials delivered securely (never by email/chat); the integration secret generated by GCO.
- Agreed acceptance scenarios, data-retention terms, incident contacts and volumes.
- The CEO's written go-live approval.
