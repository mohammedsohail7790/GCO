# Phase F - production integration adapter + first-conversation validation

**Outcome: B - infrastructure ready, real-client validation blocked.** No real provider or client integration is selected or specified anywhere in the repository, so none was invented. What was built is the first production-capable adapter that needs no third-party credentials - GCO's own signed-webhook contract - and it was validated end to end against a local client simulator.

## 1. Executive summary
- Provider search: the only provider named in the repo is Paxmod, a synchronous AI moderation API with no webhooks and no conversation channel (confirmed in `docs/GCO_PAXMOD_PLATFORM_API_DISCOVERY_REVIEW.md`); it cannot carry client conversations. `docs/client-capability-matrix.md` lists channels (WhatsApp, Instagram, custom API ...) as *client-specific, needs client credentials*; no first client or API spec exists. So no real provider can be implemented, and none is claimed.
- Built: the explicit `productionCapable` adapter contract, the `gco-webhook` adapter (inbound + outbound + verification), an SSRF-safe outbound HTTP client, pre-go-live integration verification, real delivery semantics, go-live hardening, and tests.
- `dev-mock` remains non-production. **REAL PROVIDER VALIDATION: BLOCKED** (needs a real client to implement the contract - section 19).

## 2. Adapter architecture
`IntegrationAdapter` now declares `productionCapable` explicitly (never inferred), plus optional `validateInbound`, `validateConfig`, `isPing`, `verifyOutbound`. `sendOutbound` receives a context (integration id, tenant id, secret) and returns a classified result (`delivered`, `retryable`, `failureCategory`, `latencyMs`). `dev-mock = false`, `gco-webhook = true`. `ALLOW_DEV_ADAPTERS=true` (local/CI only; unset in production) lets `dev-mock` pass the gate and relaxes the outbound-URL checks for loopback test clients.

## 3. Provider selected
None (see 1). The adapter implements GCO's published contract: `docs/gco-webhook-contract.md`.

## 4. Provider configuration
Per integration: `config.callbackUrl` (non-secret, validated at creation) and the integration's own webhook secret (generated by GCO, shown once, never listed). No environment-level provider credentials exist or are needed. Nothing was committed or printed.

## 5. Webhook (inbound) flow
Rate limit per integration -> integration lookup -> (staged DISABLED: only a correctly signed ping is accepted, recording inbound verification; everything else 404) -> tenant active / volume cap -> signature (HMAC over `timestamp.body`, +/-5 min window, timing-safe) -> JSON parse -> ping short-circuit -> **structural validation before persistence** (new; malformed payloads are no longer stored) -> dedup (body hash / event id) -> persist -> enqueue -> 202. Message-level idempotency is in the existing ingest step.

## 6. Outbound flow
Operator `POST /messages/send` (operator only; same tenant; must hold the active assignment; AI never calls it) -> persisted `PENDING_REVIEW` -> queue -> `outboundDeliveryProcessor` -> adapter -> signed HTTPS POST to the client's callback. **DELIVERED only when the client answers 2xx.** Retryable (timeout, network, 408/425/429, 5xx): message FAILED, job throws, BullMQ backoff, same `Idempotency-Key`. Permanent (other 4xx, 401/403 = wrong secret, redirect, unsafe destination, oversized response): FAILED, **no retry**, content-free `delivery` SystemEvent. A delivered message is never re-sent.

## 7. Tenant routing
The webhook URL carries the integration id; the secret is per integration, so another client's URL with this client's secret is 401. Outbound uses the message's own tenant's ACTIVE integration. Verified with two tenants (E2E 25).

## 8. Idempotency
Inbound: identical body -> one stored event, one message. Outbound: stable `message_id`/`Idempotency-Key` on every attempt; a DELIVERED message short-circuits. Limitation: delivery is at-least-once (a 2xx that never reaches GCO causes a retry) - the client must dedupe on `message_id` (documented in the contract).

## 9. Failure and recovery
| Failure | Persisted | Retry | Visible | Recovery |
|---|---|---|---|---|
| Provider timeout / network | message FAILED + event | yes, backoff | DELIVERY_FAILED event; DLQ + SystemEvent if exhausted | automatic / DLQ requeue |
| Provider 5xx / 429 | FAILED + event | yes | same | automatic |
| Provider 4xx / 401 / 403 | FAILED + event | **no** | `delivery` SystemEvent | fix client endpoint/secret, requeue |
| Redirect / unsafe or oversized | FAILED | no | SystemEvent | fix config |
| Invalid signature / stale / malformed | nothing | client retries | 401/400 | - |
| Duplicate inbound | nothing new | - | 200 deduplicated | - |
| Integration not ACTIVE for outbound | message not delivered | job fails/retries | job failure -> DLQ | activate / fix |
| Redis/queue down at inbound | event persisted, re-enqueued on the client's retry (existing) | yes | 5xx to client | client retry |
Not simulated with real outages here: DB-down, Redis-down at runtime and worker restarts (covered by Phase D/E tests and existing specs 02, 09, 18); documented rather than re-faked.

## 10. Security
SSRF-safe outbound client (https only, public hostnames, no credentials/fragments/non-default ports, no redirects, DNS-rebinding-safe address check at connect time, 64 KB response cap, generic error text). Secrets: HMAC key only, never in config/audit/SystemEvents/logs (tested), response bodies not logged. Replay: timestamp window + dedup. Config cannot carry unknown keys or self-declared verification. Rotation clears verification.

## 11. RBAC
Integration create/rotate/verify: CEO only (unchanged `INTEGRATION_MANAGE`). Go-live: CEO only. Manager/Assistant/Operator/Client/Hunter: 403; anonymous 401 (E2E 25, 24). Sending: operators only.

## 12. First-client go-live runbook
Closed Won -> BPO handoff -> tenant -> client invitation + password (Phase E) -> **create `gco-webhook` integration staged DISABLED with the client's `callbackUrl`** (secret shown once, delivered securely) -> client implements the contract -> **verify outbound** (`POST /admin/integrations/:id/verify`) and have the client send a **signed inbound ping** -> assign an operator -> confirm supervisor, languages, coverage -> checklist complete -> CEO **go-live** (activates only the verified integration) -> client sends the first real message -> operator replies -> confirm delivery on the client side.

## 13. First-conversation smoke test
Contract-level, against a local client simulator, full stack: configure -> staged ping rules -> verify both ways -> go-live -> signed inbound -> authenticated -> persisted -> queued -> assigned -> operator reply -> outbound to the simulator -> DELIVERED on 2xx -> audit trail -> other tenant sees nothing; plus 5xx recovery and 4xx permanent failure (E2E 25, 11 tests, passing). **A real-client smoke test was NOT run: REAL PROVIDER VALIDATION BLOCKED.** No production business data was created.

## 14. Metrics (local, controlled, single run - not an SLA)

## 18. Known limitations
No real client or provider validated; one adapter only (no multi-provider); at-least-once outbound delivery; the onboarding console has no integration buttons yet (verification is an API call); a permanently failed message needs manual follow-up (no requeue UI); inbound dedup for batch payloads is by body hash (message-level idempotency covers re-grouped retries); an unanswered conversation is re-assigned every SLA interval without a cap (see section 20).

## 19. What is needed for the real validation
A real first client that (1) agrees to implement `docs/gco-webhook-contract.md` (or a specific platform whose API spec/credentials GCO is given for a new adapter), (2) a staged tenant, (3) their `callbackUrl` and a secure channel for the one-time secret. No GCO-side credentials are required.

## 20. Pre-existing audit noise (`assignment.expired`) - finding, action held
Production has one stale demo conversation (an unanswered inbound message from 2026-09-28) on the demo tenant with one available demo operator. By design (E2E 04) every expired SLA reassigns the conversation, so it cycles every 120 s: 5,403 expired assignments and 5,543 of 5,561 audit rows are this loop (~720 rows/day). It is demo-only data today, but the same unbounded loop would apply to any unanswered conversation of a real tenant. No conversation-close API exists; the safe options both change production data (close that one conversation, or set the demo operator offline), so **no action was taken** - see the final report. Recommended engineering fix: cap consecutive SLA expiries and escalate/flag for a manager.

## 21. Recommended Phase G
